# Baseline review: Apex Sentinel v1.3.1

This review describes the pre-agent commit. See ../../README.md for the v2 agent and ../MIGRATION.md for changes made in response.

Reviewed 16 September 2026. Repository: [Kohap/apex-sentinel](https://github.com/Kohap/apex-sentinel), version 1.3.1, commit [`170de69e063107dcf3d9270e552411a150b8887f`](https://github.com/Kohap/apex-sentinel/tree/170de69e063107dcf3d9270e552411a150b8887f).

## Assessment

Apex has useful principles: reproduce claims, challenge false positives, retain evidence, and never fabricate findings to fill a report. The problem is that its executable checks do not reliably enforce those principles, and its output policy is optimized for bounty disclosure rather than helping a project owner repair defects.

The strongest demonstrated problem is contradictory validation: a fully populated six-gate checklist is rejected, but a newly scaffolded audit with no experiments passes the combined report gate. Separately, no Apex-owned repair deliverable is required or validated.

These are verified repository issues and plausible contributors to the reported vague output. Without an actual past report and its execution artifacts, this review cannot establish which issue caused a particular audit's result.

## 1. A logic error rejects every detected confirmed finding

**Priority: fix first. Reproduced locally.**

In [claim_gate.py, lines 70–76 and 96–105](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/claim_gate.py#L70), `has_all()` returns a list of missing names. When all six names exist, that list is empty. `jail_all_pass()` treats the empty list as false and returns false instead of checking the PASS rows.

The caller at lines 156–160 first rejects missing names and then calls this inverted helper when none are missing. Consequently, every confirmed finding ID recognized by this path gets a failure, even with six explicit PASS rows.

**Observed:** six PASS rows returned false; the command reported `jailbreaker six gates are not all PASS`.

**Repair:** correct the inverted condition, then validate all six individual rows. Merely reversing the condition leaves another weakness: the implementation requires only one PASS and no explicit FAIL, which would still allow blank results for other rows. Require a result and nonempty supporting evidence for each required check.

**Acceptance:** six complete PASS rows succeed; one missing, blank, failed, or unsupported row fails with the exact row identified. Passing the checklist must remain separate from proving the underlying vulnerability.

## 2. An untouched scaffold receives an overall report-gate PASS

**Priority: fix first. Reproduced locally.**

I ran the repository's scaffold and immediately ran its combined report gate, without conducting an audit. It returned:

```text
OK — owners have artifacts on disk.
CLAIM GATE PASS — honest empty report, no CONFIRMED rows.
APEX REPORT GATE PASS
```

There were no experiment files, and both coverage.md and final.md were empty.

The [scaffold pre-populates the no-finding statement](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/vendor/ragnarok/scaffold.sh#L231). [Component validation](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/component_check.py#L26) relies heavily on text length and a limited placeholder pattern, allowing scaffold text to satisfy artifact checks. The [claim gate's empty-report branch](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/claim_gate.py#L138) returns success without evidence of work completed.

A report-validity check can legitimately accept a statement that makes no claims. The defect is presenting that result without separately enforcing or reporting engagement completeness. The skill permits an honest empty close, but no executable close check requires a useful coverage or limitations summary.

There is also a narrower fail-open behavior: claim_gate.py pointed at a nonexistent research directory returns success and claims a gauntlet and harness are present. The combined wrapper still rejects a missing report, so this is not a demonstrated complete-wrapper bypass.

**Repair:** separate report validity from engagement status. A fresh scaffold is NOT STARTED. A blocked audit is BLOCKED or PARTIAL. A completed no-finding audit must include checks performed, evidence references, untested surfaces, blockers, and next actions. Missing required inputs must not produce a claim of verified evidence.

**Acceptance:** untouched scaffolds and missing directories cannot be reported as completed audits; a documented completed audit can finish with zero confirmed findings.

## 3. The evidence checks mostly verify words and file presence

**Priority: fix alongside item 1. Local reproduction plus source inspection.**

The [vendored report checker](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/vendor/ragnarok/report_gate.sh#L94) accepts status markers, an arbitrary file under experiments/, and sufficiently long prose under three headings. It does not verify that a reproduction ran or that its output supports the claim.

**Observed:** that checker accepted a synthetic report containing no reproduction command, measured impact, source location, or repair instructions. Its only experiment file was note.txt, explicitly saying no test had run. This was the vendored checker in isolation; the combined Apex wrapper failed because of item 1.

Additional source-level gaps in [claim_gate.py](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/claim_gate.py#L161):

- Question names are sufficient for several checklist checks; answers are not parsed.
- Runtime and economic verification markers are searched across the whole hypothesis document rather than tied to each finding.
- Experiment existence is not linked to the finding or a recorded run.
- No Apex-owned check requires a remediation or regression-test specification.

**Repair:** store each finding as a structured record, then generate the readable report from it. Tie its source revision, reproduction, execution command, exit status, captured output, observed behavior, and evidence files to the same finding ID. Check file references and assertion results. Keep semantic review: a schema and a passing test alone do not prove a security claim.

**Acceptance:** an unrelated note, another finding's run, missing command output, or a missing repair specification cannot satisfy a confirmed finding's requirements.

## 4. The saved report status can disagree with the overall result

**Priority: next. Reproduced locally.**

The [Apex wrapper](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/report_gate.sh#L25) allows the vendored checker to write report-state.md before aggregating all checker results.

**Observed:** running the wrapper with --write produced an overall failure and exit code 1, while report-state.md recorded `Report gate: PASS`. That file describes only the vendored result, but its name and wording do not make the distinction clear. An agent resuming from disk could read a misleading success signal.

**Repair:** write the aggregate manifest once all checks finish, with the overall result, individual results, reasons, source revision, and evidence references. Label component-only statuses explicitly.

**Acceptance:** whenever any required checker fails, the saved overall state is FAIL.

## 5. The rules prioritize bounty eligibility over project repairs

**Design mismatch with your stated frontend/backend use case.**

[SKILL.md lines 265–281](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/SKILL.md#L265) restrict report.md to CONFIRMED-REPORTABLE findings and require Critical/High severity, quantified asset loss, and a permissionless exploit before disclosure. Medium/Low findings are directed to final.md and the Brain. Confirmed findings generally also require economic verification.

This can be appropriate for a deliberately narrow bounty campaign. It is an awkward default for a project owner who needs privacy leaks, authorization defects, availability failures, and other application problems explained and repaired. Those defects do not all have a meaningful attacker-profit or asset-loss calculation.

The APPLICATION route skips parts of EVM reconstruction, but [P5 and P6 load cards](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/load_card.sh#L83) still prescribe EVM-oriented tools and economic accounting. The application guidance is concentrated on a transaction-execution workflow rather than a general frontend/backend workflow.

**Repair:** introduce explicit `project-review` and `bounty-hunt` modes. Separate these decisions:

1. Is the defect confirmed?
2. What is its demonstrated impact and priority?
3. Is it eligible for a particular external disclosure program?

In project-review mode, all confirmed defects should appear in the repair queue regardless of bounty eligibility. Application impact can be unauthorized records accessed, actions performed, secrets exposed, or service disruption, with appropriate measured bounds. Keep uncertainty visible and retain the prohibition on fabricated findings.

## 6. Developer handoff is not an enforced deliverable

**Direct contributor to unactionable output.**

The P9 workflow routes to external component report templates, but the repository's own checks do not require an exact fix or an acceptance test. Its [scaffold creates final.md as an empty file](https://github.com/Kohap/apex-sentinel/blob/170de69e063107dcf3d9270e552411a150b8887f/scripts/vendor/ragnarok/scaffold.sh#L12), with no enforced repair structure. This review did not audit the separately installed component skills; they may provide stronger guidance, but Apex does not guarantee that guidance survives into its final output.

**Repair:** require a developer task for each confirmed defect containing:

- Affected revision, file/function, and reachable route or entry point.
- Preconditions and safe reproduction steps.
- Expected behavior, observed behavior, and linked evidence.
- Demonstrated impact and explicit limits.
- The precise behavior to change and where it is enforced.
- A regression check that demonstrates the bug and checks the intended repair, plus a legitimate-use control case.

Unresolved leads need their own next verification step and blocker. They should not be presented as confirmed repair tasks. When there are no confirmed defects, deliver the coverage and blocker summary rather than a one-sentence empty report.

## Additional compatibility issue

The Apex instructions introduce CONFIRMED-REPORTABLE and CONFIRMED-INTERNAL labels, while the vendored report checker recognizes only a ledger row ending in the literal CONFIRMED. In the synthetic fixture, changing only the final status from CONFIRMED to CONFIRMED-REPORTABLE changed the vendored result from PASS to FAIL. The scaffold documents the older ledger vocabulary, so using separate ledger status and reportability fields can avoid this; the current documentation should make that distinction explicit. A shared structured state model would eliminate the ambiguity.

## Recommended shipping order

1. **Reliability patch:** fix the six-gate logic; reject missing inputs; report aggregate status correctly; distinguish a valid empty report from a completed audit. Add behavioral tests for these demonstrated failures.
2. **Actionable project-review mode:** separate confirmation from bounty eligibility and require a repair task for every confirmed issue.
3. **Evidence and fix verification:** connect findings to reproducible runs and support rerunning those checks against a proposed repair.

Evaluate the new behavior on small local projects with known defects and clean controls. Include a cross-account access failure, a synthetic secret exposure, an intentional privileged operation that is not a vulnerability, a blocked test environment, and a completed no-finding run. Measure confirmed-finding accuracy and whether a developer can reproduce and repair each issue from the output alone. These are proposed future evaluations, not tests performed in this review.

## Validation and limits

The repository source was left unchanged. Testing used local synthetic fixtures and the bundled scaffold/validation scripts; no live target was audited and no external disclosure occurred. The separate component repositories and historical audit outputs were not evaluated.

[Raw check results](./apex-review-checks.json) include the observed exit codes and output. The six-PASS helper assertion, untouched scaffold result, missing-directory result, note-file acceptance by the vendored checker, conflicting saved status, and status-label mismatch were all reproduced successfully.
